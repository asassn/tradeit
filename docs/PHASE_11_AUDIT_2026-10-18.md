# Phase 11 audited — the first phase where the audit finds missing code

Audited 2026-10-18, the fourth phase audited this way. **The pattern that held
for Phases 7, 8 and 9 breaks here, and that is the finding.** Those three were
built and unexercised. Phase 11 is genuinely part-built, and the missing parts
are the ones the phase is named after.

## The requirement

> Cost and fill models, paper broker, execution service with reconciliation,
> trade journal, running on the live code path with a simulated venue.

## The audit

| requirement | state | evidence |
|---|---|---|
| cost model | **built and exercised** | `ParticipationCostModel`, used in every real-data backtest this project has run |
| fill model | **built and exercised** | `BarFillModel`, same |
| order/execution/trade/journal **schema** | **built** | `orders`, `executions`, `trades`, `journal_entries` tables exist |
| execution service with reconciliation | **declared, not implemented** | `ExecutionService` is a `Protocol` in `execution/base.py`; `grep` finds no implementation anywhere in `src/` or `tests/` |
| paper broker | **does not exist** | no `PaperBroker` or equivalent in the tree |
| trade journal writer | **does not exist** | `JournalEntry` is a table with no repository and no writer |

`src/tradeit/execution/` is 455 lines in two modules, with 23 tests on the
simulation half. The protocols are 202 of those lines.

## What this means for the estimate, said plainly

**Phases 8 and 9 closed in a day each because the work was already there and
auditing it *was* the work.** That cannot repeat here. Phase 11 needs code
written: a broker that accepts orders against a simulated venue, a service that
places and reconciles them, and a journal that records what was decided and
why. The schema is waiting for all three, which is real progress and is not the
same as the phase being nearly done.

**This does not move the 2026-11-21 target yet**, and the honest reason is that
the target was set on the assumption Phase 11 needed building — it is the one
Track A row that was never described as "partly exists". The audit confirms the
assumption rather than overturning it.

## What the audit does change

Two things worth recording before the work starts, both found by reading rather
than by running:

**`ExecutionService.reconcile` returns `list[str]`.** A reconciliation that
reports discrepancies as strings cannot be acted on programmatically — it can
be logged and read by a person, and nothing else. For a paper venue that is
tolerable; for the live path Phase 12 gates, a discrepancy needs to be a value
with a type, an affected position and a magnitude. Flagged now because the
protocol is cheap to change today and expensive once two implementations
depend on it.

**`JournalEntry` has no repository, and the journal is described in its own
docstring as "append-only, and the system's memory".** An append-only record
with no writer is a table, not a memory. Whatever writes it should be the only
thing that can, and that is easier to arrange before there are two callers.

Neither is a defect in shipped behaviour: nothing uses either path yet. Both are
the kind of decision that is free now and a migration later.

## Status

**Phase 11 is not closed and is not nearly closed.** Two of its five parts are
built and well exercised, the schema for the other three exists, and the three
components the phase exists to deliver are absent. Target stays **2026-11-21**.

Phase 7's Swing path is exercised but **not wired into selection**, which is the
one open question in front of Phase 11 that cannot be settled by measurement —
wiring score 3 changes what every backtest means, so it needs a scoped
proposition rather than a commit.

# Addendum, 2026-10-18 — three of the three missing parts, built

The audit above found Phase 11's two models built and exercised, its schema
present, and the three components the phase is named after absent. All three
now exist, and the two protocol decisions the audit flagged were taken first —
which was the point of flagging them.

## One correction to the audit above

**The audit said the journal has "no repository and no writer". That was right
about the trade journal and arrived at carelessly.** It was concluded by
grepping `storage/repositories.py`, and a writer elsewhere in the tree would
have been missed. One nearly was: `src/tradeit/acquisition/journal.py` defines
its own `JournalEntry` — a JSONL row about a download — and the first version
of the single-writer test flagged it as a second writer.

It is not one. **It is a name collision between two unrelated concepts**, which
is exactly what this project's *keep similar concepts apart* discipline warns
about. The collision is recorded and pinned by a test rather than fixed by
renaming an established module as a drive-by.

## The two protocol decisions, taken before any implementation

**`reconcile` returns `tuple[Discrepancy, ...]`, not `list[str]`.** A
`Discrepancy` carries its kind, the instrument, both views and a note. A halt is
the easy half of reconciliation; the hard half is *what is wrong, by how much,
and where*, and a string can be logged but not compared against a tolerance,
aggregated, or used to tell a rounding artefact from a missed fill.

`magnitude` returns **`None`** when one side has no value, not `0`. The distance
from a number to an absence is not a number, and a `0` reads as agreement — the
specific mistake the `None` exists to prevent, now pinned by a test and killed
by a mutant.

**The journal has one writer and no update path.** Append-only is a property of
how a table is used, and SQL offers no way to forbid an UPDATE to a caller
holding a session, so the discipline is structural: `execution/journal.py` is
the only module that constructs the ORM model, and a test walks `src/` asserting
it. Weaker than a database constraint, stronger than a docstring, and chosen
before a second caller existed.

## What was built

**`execution/paper.py` — a simulated venue that behaves like a venue.** The
split that matters is temporal: `submit_order` **accepts and fills nothing**,
returning `NEW`, because that is what a venue says when it has taken an order
and the market has not traded against it. `advance(session_date, bars)` then
trades one session against the resting orders. **The structure, not a comment,
is what prevents an order filling against a bar that had not printed when it
was placed.**

It reuses the backtester's own `BarFillModel` and `ParticipationCostModel`
rather than carrying its own, so a paper fill and a backtest fill of the same
order against the same bar agree by construction.

Refused rather than modelled, each because modelling it would mean inventing
evidence: **short selling** (borrow availability), **margin** (buying power
equals cash, stated rather than inflated), **fractional shares**, and
**carrying an unfilled remainder overnight** — `TimeInForce.DAY` means the day,
and a survivor would be a GTC order nobody asked for.

It **refuses to be constructed where orders are not simulated** (ADR-0004),
checking for itself rather than trusting its caller.

**`execution/service.py` — the halt.** The broker is authoritative; our state is
a model of it. On any disagreement the service halts that portfolio and `place`
refuses, because every decision after a disagreement is computed from a book
that does not exist. **A service that logs a discrepancy and keeps trading has
chosen the worst of both.**

A halt is **sticky**: a later reconcile that happens to agree does not clear it.
Clearing requires `resume(resolved_by=..., note=...)`, both mandatory, so it is
an event somebody performed. A transient disagreement that resolves itself is
precisely where silence is most dangerous.

**Quantities compare exactly; cash and average price compare against a
tolerance** with no default, because they accumulate rounding through commission
splits and partial fills and halting on a half-cent would mean halting daily. A
tolerance on a share count would hide a missed partial fill, which is the
commonest real cause.

**`execution/journal.py` — what was passed over.** `record_entry` takes
`rejected` and writes it into the context, rather than leaving each caller to
remember: a record of what was bought explains nothing, because the question
later is never *what did we buy* but *why that one*, and the answer is the slate
it beat. Decimals are stored as **strings**, since `float(Decimal)` loses
precision on exactly the values a journal holds. An over-long summary **raises**
rather than being truncated into a corrupted record. It **does not commit** — a
journal entry belongs in the same transaction as what it describes, or it can
survive a rollback and confidently describe a trade that never happened.

## Two things the mutation testing found

Twelve mutants were run across the three modules. Two revealed tests that
proved nothing:

**A sell cap test that passed with no cap.** It asserted only that the position
ended empty — and a mutant removing the cap drove the holding to **−400
shares**, which `list_positions` hides because it filters non-positive
quantities. An impossible short read as a clean exit. The test now asserts the
filled quantity and the cash received.

**A session-date default that the linter caught before a test did.** `reconcile`
first stamped journal entries with `date.today()`. `ruff` flagged the naive
call, and the real problem was larger than style: a reconcile run after midnight
UTC, or replayed over history, files itself under the wrong trading day and
corrupts the one record meant to explain what happened when. `session_date` is
now required on both `reconcile` and `resume`, and on the protocol.

## Status

**Phase 11's components exist and are unit-tested; it is not closed.** What is
built has never run against the corpus — the same gap Phases 7, 8 and 9 carried,
and the one that took a day each to close there. Still owed: an end-to-end paper
session over real bars, and the reconciliation loop driven from a real portfolio
rather than a constructed `PortfolioState`.

Target stays **2026-11-21**.

# Second addendum, 2026-10-18 — the corpus exercise, and the two defects it found

The components were unit-tested and had never seen the corpus. They have now,
and the exercise did what it was built to do: **it found two real defects, one
of them outside Phase 11 entirely.**

## The claim, and how it was tested fairly

> Paper and backtest share a code path, so a paper fill and a backtest fill of
> the same order against the same bar agree.

If that holds, a paper result is evidence about the simulated strategy. If it
does not, paper trading measures a second undocumented system.

**Both paths are driven from the same decisions.** The backtester runs normally
and every order it places is captured with the bars of the session it settled
against; those same `OrderRequest` objects are then submitted to `PaperBroker`
and advanced over the same bars. **Nothing re-decides**, because a second
independent run would diverge for ordinary reasons — different cash, therefore
different sizes, therefore different fills — and would say nothing about the
venue.

**The venue is given a float rather than the strategy's capital**, and that is
the difference between isolating the venue and not. The first run used equal
capital and reported **289 of 330 fills differing on quantity** — which measured
the two cash balances drifting apart, not the fill arithmetic. The venue's own
cash cap is therefore excluded here by design and covered by its unit tests.

## Result: 1,457 of 1,457 fills agree exactly

On 195 SIC-classified names over 2010–2019: 802 trades, 1,470 order
submissions, **1,457 fills agreeing exactly on quantity and price. Zero
disagreements.**

That is after fixing what the exercise found. It did not start there.

## Defect 1 — the engine's order ids were not unique, against a `unique=True` column

The first replay refused nine submissions: *"client_order_id 'e-3639' was
already used for a different order"*. The engine built its ids as
`f"e-{instrument_id}"`, so **every entry order for one instrument over a
ten-year run shared a single id.**

Nothing inside the backtester noticed, because it tracks pending orders in a
list and never reads the id. It matters for two reasons the backtester cannot
see:

* **`orders.client_order_id` is declared `unique=True`** in the schema, and its
  docstring calls it unique. Persisting these orders would violate the
  constraint.
* **`OrderRequest`'s own contract** says the id is what makes a retry safe —
  *"resubmitting the same id is a no-op at the broker rather than a second
  position"*. Pointed at a real broker, a second entry in the same name would be
  swallowed as a duplicate or rejected.

Fixed by including the session: `e-{instrument_id}-{session_date}`. One entry
per instrument per session is already guaranteed — `PortfolioCycle.plan` raises
on duplicate candidates for one instrument — so the id is unique. A test pins it
and fails against the old form.

**This defect was in Phase 9's engine, not Phase 11.** It was invisible until
two components built in different phases were connected, which is the argument
for connecting them before Phase 12 rather than after.

## Defect 2 — the paper venue ignored corporate actions

With ids fixed, **1,456 of 1,457 agreed**. The one disagreement was an exit of
312 shares against a venue holding 208.

Two hypotheses were checked and refuted before the right one was found, which is
worth recording because the first was plausible:

1. **A carried order.** The engine carries an unfilled order when an instrument
   did not print; the venue cancels it as a DAY order. Measured: **zero carried
   orders in the run.** Refuted.
2. **A corporate action in `corporate_actions`.** That table holds **zero rows**
   for the instrument. Refuted — and this is why the first guess was wrong
   rather than merely unlucky: research-01 sources splits through
   `recorded_splits`, not that table.

`recorded_splits(session, 2322)` shows a **1.5 ratio split with ex-date
2014-05-20**, a month before the exit. 208 × 1.5 = 312. The engine applies
splits in `_apply_splits`; the venue did not apply them at all.

**A real broker applies the split to the real account.** A paper venue that does
not will drift from our book after every split — and it is the case
`ExecutionService` names, inverted: there the worry is an action the broker
applied and we missed; here we applied it and the venue did not. Reconciliation
would have halted on it, correctly.

`PaperBroker.apply_splits` now restates holdings and resting orders, with the
total cost basis unchanged so a split moves no money. 75 sessions in the run
carry one. With it, **every fill agrees**.

## A third finding, pinned and deliberately not fixed

**`market_impact` is zero on every fill this project has ever produced.**
`ParticipationCostModel` computes impact only when handed an
`average_dollar_volume`, and **neither the venue nor the backtester's `_settle`
passes one** — so `CostConfig.market_impact_coefficient` has had no effect on
any backtest, and `participation_rate` is always 0.0.

Found by a test that failed against correct code: a first version varied the
reference bar's *volume*, which the cost model ignores without that argument.
The close is what the reference bar actually feeds through.

**Not fixed.** Cost assumptions are explicitly a scoped proposition in this
project, and switching impact on would move every published result. Pinned by a
test so the next reader finds it stated rather than assuming impact was modelled
and found not to matter — the same mistake `correlation_weight=0.0` invited for
a year.

## One divergence found by reading rather than running

The backtester estimates cost against the bar the decision was made on and
fills against the next, and `BarFillModel` derives slippage from that estimate —
so **the reference bar sets the fill price.** A venue estimating against the bar
it is filling on would price every paper fill differently while appearing to
share the code path. `PaperBroker` keeps the last bar it saw per instrument,
which at submission time is the decision bar. A mutant swapping them passed all
twenty-five other tests in the file, so it now has one of its own.

## Status

**Phase 11's components are built, unit-tested, and exercised against the
corpus, with paper/backtest equivalence demonstrated order by order.** Still
owed before closure: the reconciliation loop driven from a real portfolio rather
than a constructed `PortfolioState`, and a session where the venue — not a
replay — is the thing deciding what it holds.

Target stays **2026-11-21**.
